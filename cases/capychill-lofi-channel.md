| **時間範圍** | 2026-06 起,2026-07-28 後停擺 |

| **一句話結論** | 我以為卡在產能,其實卡在發佈;而讓它停下來的,是成功的隔天做的一個決定。 |

---

## 1. 原本的問題

做一個 lofi 陪伴電台頻道:一隻水豚戴著耳機,固定機位,30–60 分鐘的長片,配自己生成的音樂。

計畫寫得非常細 —— 細到現在回看有點刺眼:

- 每月 400 點額度精算到三段:200 點跑 20 次 Veo Lite 探場景、120 點跑 6 次 Fast 做高品質循環、80 點留給重做
- 影片長度對應素材量寫死:30 分鐘 6 段微動畫、45 分鐘 8 段、60 分鐘 10 段
- 動畫品質底線寫成規則:雨只能向下、煙只能向上、首尾姿勢要能循環、相機不准動
- 每天一個工作資料夾,`concept/ video_raw/ music_raw/ audio_mp3/ edit/ export/`

**第一個月的交付節奏也寫清楚了,而且寫對了:**

> 第 1 週先選定**唯一**主場景與**唯一**角色位置,建立同構圖的白天、黃昏、夜晚版本。第 2 週組成第一支長片。**第 3 週只在同一構圖增加雨天或季節版本,不更換房間與角色位置。** 第 4 週發布並觀察數據。

請記住這一段。三天後它會被推翻。

## 2. 第一版怎麼做的,為什麼不行

第一版做成了。**這是這個案例最反直覺的地方 —— 它不是失敗在做不出來。**

`DailyPrompt/20260724/export/` 裡躺著:

```
20260724_CapyChill_1080p.mp4    3.8 GB    1920×1080    1742 秒(29 分 02 秒)
建立時間:2026-07-25 02:27
```

一支完成的 29 分鐘 lofi 長片。音軌合好了、循環接好了、`edit/` 裡有 `album_master.mp3` 和 `video_bed_1080p.mp4` 的中間檔,組裝腳本 `build_daily_album.py` 跑通了。

**它從沒被上傳過。**

然後看接下來三天的資料夾:

| 日期 | 音樂 MP4 | 動畫循環 | 成片 |
|---|---|---|---|
| 07/23 | 10 支 | 0 | 無 |
| **07/24** | **10 支** | **6 支** | **✅ 29:02** |
| 07/25 | 8 支 | 0 | 無 |
| 07/26 | 10 支 | 0 | 無 |
| 07/27–07/31 | 0 | 0 | 無(只有 prompt 文件) |

**做出成片的隔天開始,只囤音樂,不生動畫,不出成片。** 28 支音樂 MP4 堆在那裡 —— 足夠再做兩張專輯 —— 但沒有一支動畫循環可以配。

七天後,整個專案停了。到今天 44 天。

## 3. 轉折點:哪一個決定改變了結果 ⭐

> **這段留給 SS 補。下面是我從檔案時間戳裡挖出來的候選,選一個或改寫。**

**候選 A ── 7/25 那天,規則從「重複同一場景」改成「每天一個原創場景」**

`DailyPrompt/README.md` 的「已鎖定決定(2026-07-25)」寫著:

> 7/25 起採用「**每天一個原創場景**」的規則;固定的是水豚角色身份、暖色手繪語言……**不固定房間、家具、角色位置、配角或天氣**。7/30 使用竹林溪畔茶亭與小紅熊貓;7/31 使用閣樓唱片室與小灰貓,不循環重複 7/23 海邊或 7/24 雨中溫室。

這跟 `PRODUCTION_PLAN.md` 的「第 3 週**只在同一構圖**增加雨天版本,**不更換房間與角色位置**」是**直接矛盾**的。同一個專案的兩份文件,寫了相反的紀律,而後寫的那份贏了。

日期值得注意:成片是 **7/25 凌晨 2:27** 完成的,這個決定就在**同一天**。

**它把每天的工作量從「換音樂 + 重跑腳本」變成「重新設計一個房間 → 重生母圖 → 重生動畫 → 重新組裝」。** 而這個決定,是在剛嘗到成功、精神最好的那個當下做的。

**候選 B ── 同一天,手掌規格改版,等於宣告舊母圖全部作廢**

7/25 的概念圖 Prompt 加上了 `PAW CONSTRUCTION` 規則,說明寫著:

> 舊概念圖的手是圓團,動畫階段一定不動;**影片還沒生成的日子請用這版重生母圖。**

技術上這個修正是對的(mitten 手掌確實動不了)。但它跟候選 A 疊在一起,同一天把待辦從「照著跑」變成「全部重來」。

**候選 C ── 成片做完的當下沒有上傳**

7/25 凌晨兩點半導出 3.8GB,那個時間點大概只想睡覺。但「明天再傳」之後,再也沒有明天 —— 因為隔天的注意力全部被新規則吸走了。

> **我的判斷是 A,B 是加速器,C 是致命傷。**
> A 決定了它會慢慢死,C 決定了它死掉時什麼都沒留下 —— 如果那支片 7/25 就上傳了,7/28 會有第一批數據,而數據是唯一能把人拉回專案的東西。
>
> **SS 你自己記得當時在想什麼?這段照你的記憶改。**

## 4. 最後的架構

| 層 | 實際狀況 |
|---|---|
| 🧠 **Model** | 影片 Veo 3.1(Flow「帧」模式,首尾同圖鎖 zoom 做循環);音樂 Gemini;概念圖另外生 |
| 🎭 **Project** | ✅ 做得最好的一層。角色身份、暖色手繪語言、固定機位、NEGATIVE 清單、RULES 六條,每天的 prompt 自帶完整規則,單獨複製就能用 |
| 🧩 **Skills** | ✅ 也很紮實。動畫品質底線寫成可檢查的規則(雨只能向下、煙只能向上、首尾要能循環、每個可動元素要有獨立空氣路徑) |
| 🔌 **MCP / 工具** | ❌ 全手動。Flow 和 Gemini 都是人去網頁生成、下載、歸檔 |
| 🔄 **Workflow** | ⚠️ **只做了中段。** 組裝自動化了(`build_daily_album.py` 一行指令輸出橫版 + 直版 + Shorts),但**進料靠人、發佈也靠人** |
| 📚 **Knowledge** | ✅ Markdown + 日期資料夾,規則和決策都留在 repo 裡 —— 所以 44 天後還能被完整重建出這篇案例 |

**看這張表就懂了:六層裡做得最好的是 Project 和 Skills,唯一有缺口的是 Workflow 的頭尾兩端。**

而缺的那兩端,剛好一端是「每天要做的美感決定」,一端是「按下上傳」。**一個消耗意志力,一個需要勇氣,兩個都是人味最重的部分 —— 也正是自動化最該覆蓋、卻最常被跳過的部分。**

## 5. 如果重做一次,我會跳過什麼 ⭐

> **這段留給 SS 補。下面是我的觀察,當草稿。**

- **跳過「每天一個原創場景」。** 回到原計畫:一個房間,做白天/黃昏/夜晚/雨天四個版本,四支片。lofi 觀眾要的是穩定,不是新鮮 —— 換房間是滿足創作者,不是滿足觀眾。
- **跳過 400 點的精算配置。** 那份預算表寫得很漂亮,但實際只用掉一天份就停了。**在第一支片有數據之前,任何長期額度規劃都是在規劃一件還沒被驗證的事。**
- **跳過那 18 支沒配對的音樂。** 7/25、7/26 生了 18 支音樂卻一支動畫都沒生,是因為生音樂比較快、比較有成就感。**囤積容易的那一半,是拖延的高級形式。**
- **不跳過的:那四支組裝腳本。** 它們現在還能跑,是這個專案唯一還在增值的資產。

## 給讀者的一句話

**做完的東西沒送出去,等於沒做。**

而讓專案死掉的決定,往往不是在低潮時做的 —— 是在你剛完成一件事、覺得自己可以做更多的那個晚上做的。

## 這個案例對應的通則

寫進了入門包的 `05-troubleshooting.md`:

- 「一開始很勤,後來就不用了」→ 九成的原因是**你每次要用它都得做一個決定**
- 「素材做了一堆,但一個成品都沒出去」→ **在做第二批素材之前,先把第一批走完全程**

CapyChill 就是這兩條的原始出處。
